# 工程筆記

寫給下一個接手的人(多半是隔一段時間之後的自己)。
這裡只記**在原始碼裡看不出來的東西**:踩過的坑、量出來的數字、
以及某些看起來奇怪的寫法為什麼非那樣不可。

架構本身看 `README.md`,規則看各檔案開頭的註解。

---

## 一、這個專案的三條硬規矩

**1. 純邏輯不碰 three。** `src/game/**` 一律不 import three ——
所以整個規則層在 vitest 裡跑得動,空跑一千場戰鬥不需要瀏覽器。
跨界線的型別用 `import type`。

**2. 高頻資料走模組級陣列,不進 zustand。**
`fighters` / `playerPos` / `presences` / `raidParties` / `impacts` / `corpses`
每幀都在動,進 store 等於每幀通知整棵 React 樹重繪。
只有**低頻**狀態(村況、時辰、日誌、結義)才進 store。

**3. 平衡靠空跑,不靠眼睛。** `combat.balance.test.ts` 與 `tools/sim/measure.ts`。
「看起來太難」這句話量過三次,三次的真因都不是難度
(一次是傷害過高、一次是我的測試少了一個人、一次是 AI 迂迴根本沒發生)。

## 二、驗收:什麼時候該用什麼

| 要驗的東西 | 用什麼 | 為什麼不用另一個 |
|---|---|---|
| 規則、數值、狀態機 | vitest | 快、可重跑、進得了 CI |
| **幾何**(五官位置、比例、零件貼不貼臉) | vitest + 撈頂點 | 截圖驗過兩次都失敗,見下 |
| 顏色、光、後處理 | 瀏覽器探針 + **露一個數字出來** | 差幾個百分點,眼睛比不出來 |
| 構圖、氣氛、「好不好看」 | 固定機位對照片 | 只有這個能判 |

### Playwright 探針的四條鐵律

1. **`headless: false`**。無頭下 `React.lazy` 的彈窗永遠不 resolve。
2. **每次截圖前 `page.bringToFront()`**。背景分頁的 rAF 會被節流。
3. **截圖不要 `.catch()`**。吞掉錯誤等於「拍到了一張不存在的圖」。
4. **機位要自己擺**。交給鏡頭解算器的話,拍回來一張貼著牆、一張埋在樹冠裡。
   擺法:`__place(x,z)` → 等 2.4 秒 → `__freezeCam(true)` → `__setCam(cam, look)`。

### 探針常用的把手(都掛在 window,正式版不留)

```
__place / __walkTo / __walkToNpc / __setCam / __freezeCam / __cam
__setClock / __setWeather / __clock / __snow(k) / __village(order, harvest?, trade?)
__gpu / __renderInfo / __pick(px,py)      ← 從像素反查是哪個物件畫的
__post   調色/光柱/景深/接觸陰影
__sky    雲/水花/風痕/雷/積雪
__fallen 屍首/血漬/火花
__built  房子調到多「新」
__foliage 透光強度/風力
__battle 場上每個人的狀態、擋/閃/中的計數
__hideVeg(true)  整批藏起植被 —— 量成本用
__villagers / __near / __talkTo / __forceBattle / __routBand
```

## 三、量出來的數字(不要憑印象推翻它們)

| 事情 | 數字 | 結論 |
|---|---|---|
| 景深一直開著 | 7.5 → 13.3 ms | 太貴。只在說話/進場所/落幕掛上 |
| 景深 resolutionScale 0.5→0.25 | 一毫秒都沒省 | 貴的是全解析度的 CoC 與遮罩,不是散景 |
| 藏光全部植被(2800×1600) | 18.0 → 17.0 ms | 一百萬三角形、22 draw 只值 1 ms。**LOD 不做** |
| 腳邊那圈草重鋪一次 | 1.3–1.9 ms | 走一步重鋪一次划算,每幀重鋪不划算 |
| AI 迂迴包抄 | 勝率 0.43 → 0.365 | **有害**,已移除;只留玩家可用的那一半 |

**量之前先確認沒頂在天花板上。** 這一條吃過虧:第一次量植被得到
「藏光了省 0.00 ms」,而那是因為兩邊都卡在 75Hz 垂直同步 ——
等於拿兩個都爆表的溫度計比體溫。要先把視窗放大到離開上限。

## 四、踩過的坑,按類型

### 時間軸

**兩條時間軸相減 = 一個幾十秒的大數。**
`clock.elapsedTime`(從開網頁算)和 `battleTime()`(每場架歸零)不是同一條。
渲染端曾經拿前者減 `hurtAt`,於是**挨打閃紅與命中音效從來沒響過** ——
不報錯,畫面上只是「沒有回饋」。
凡是和 `hurtAt` / `guardAt` / `impact.t` 比的,一律 `battleTime()`。

### 著色器

- **編不過的材質在畫面上是純黑,不是報錯。** `vViewPos` 被讓路與透光兩個功能
  共用,各宣告一次就編不過。
- **`vertexColors` 開了而幾何沒有 color 屬性 → 整批純黑**(WebGL 給 (0,0,0))。
  草是 `instanceColor`(不能開 vertexColors),人是烘在頂點裡(要開)。兩套不能混。
- **`getHSL` 讀線性、`setHSL` 寫 sRGB。** 兩邊都要顯式指定色彩空間,
  否則抖色會把四分之一的樹抖成純黑。
- **`mergeGeometries` 要求屬性集合一致、而且「全部有索引或全部沒有」**,
  否則靜靜回 `null`。後面一個 `!` 就把整個身體弄不見了。

### 三與 R3F

- **`useFrame` 的正優先度會接管整個渲染迴圈。** 想「先清空再收集」的排程做不到,
  改成「畫的人自己畫完就清」,最壞晚一幀。
- **`gl.info` 預設每次 render 清一次**,而合成器一幀 render 好幾遍 ——
  從外面讀到的永遠是最後那道全屏 pass(1 draw、0 三角形)。
  已改成 `autoReset = false` + 一幀開頭清一次(priority −1000)。
- **透明物件永遠排在不透明之後畫**,`renderOrder` 管不到這件事。
  雲關掉 depthTest 就會蓋在山頭前面。
- **`instanceColor` 沒有 alpha。** 單一實例要淡出只有兩條路:
  往背景色靠,或者縮小。往背景色靠只在襯著天空時成立 ——
  賊窩的煙襯著山,收到底就是一個白圓(見下)。

### 「看起來像壞了」但其實是別的

- 三個掛在山腰的**白色大圓球** = 賊窩的煙(`toneMapped={false}` + 12 公尺寬)。
  掃場景樹認不出來,靠「把賊全打散前後各拍一張」對上號。
  → 之後加了 `__pick(px,py)`,從像素反查物件。
- 秋天天上飄著**幾張門板** = 落葉在鏡頭半公尺外重生,少了最小距離。
- 冬天封凍畫面對、把手卻報 `streaks: 48` = 提早 return 只清了 `im.count`,
  忘了清 stat。**畫面對而把手說謊,驗收就白做了。**

### 測試自己騙自己

- **樁子寫錯**:`slideMove` 樁回傳原地 → 全場一步沒動、25 秒後「僵局」規則發作
  不戰而散,三個計數器全零。看起來像新功能沒接上。
- **前一條測試留下來的東西**:`living.test` 清了天災還炸,
  第二個兇手是**亂兵**(phase 停在 present 就每天咬收成)。
  「把場上正在燒的東西清乾淨」要對**每一個按天生效的系統**各做一次。
- **`-0 * k === -0`,而 `toBe(0)` 會炸。** `armSwing` 顯式回字面 `0`。
- **超出 double 精度的乘同餘不是亂數。** `s * 1103515245` 會溢位;用 16807 那組。

### 幾何用幾何驗,不要用截圖

表情(眉/嘴/眼)靠截圖驗失敗兩次:把鏡頭端到人臉前面、繞四圈挑「最亮那一面」
當正臉 —— 挑回來的是後腦勺(白髮比背光的臉亮),而且那些人自己還會走開。
改成把烘了色的頂點撈出來量座標,一次就對,順帶量出
**眉毛的斜度方向和註解寫的相反**(註解說「外高內低」,實際內高外低)。

## 五、還沒做的

**大檔案拆分:做完了。** 拆的判準不是行數,是**這個檔裡的東西性質不一樣**:

| 原本 | 現在 | 拆成什麼 |
|---|---|---|
| `game/combat.ts` 1083 | 754 | + `combat/{types,tuning,state,battlefield,store}` |
| `App.tsx` 773 | 547 | + `dev/handles.tsx`(那一排 `window.__xxx`) |
| `ui/PlacePanel.tsx` 742 | 179 | + `ui/places/{Trade,Care,Rest,Civic,ctx}` |
| `world/Battle.tsx` 686 | 499 | + `world/battle/{Arrows,pose}` |

三條在拆的時候管用的原則:

1. **不要為了行數而拆。** combat 的模擬本體(754 行)沒有拆 ——
   開場布陣與每一步共用同一組節奏參數和同一顆骰子,硬拆只會讓那條線更難讀。
2. **整包傳,不要逐項傳。** PlacePanel 那十一塊用一個 `PlaceCtx` 整份遞下去,
   各自解構自己要的 —— 於是**區塊裡的每一行都原封不動**。
   拆檔最容易出事的地方就是「順手」動了幾個字。
3. **舊的 import 路徑一個都不要改。** combat.ts 檔尾補了一整批 re-export。
   拆檔是給寫這一塊的人方便,不該讓另外二十個檔跟著動。

一個實作上的坑:**ES 模組匯出的 `let` 是唯讀綁定**,匯入的那一邊改不動它。
`clock` / `rand` 這幾個原本是裸 `let`,拆檔後要收進一個物件(`sim`)才共用得起來。

**清單上唯一沒做的視覺項是 19(植被 LOD)** —— 量過兩次都不值得,
等它掉出 75Hz 上限再說。

覆蓋率的空白:`tavern` / `places` / `convoy` / `audio` 四個模組沒有測試。
